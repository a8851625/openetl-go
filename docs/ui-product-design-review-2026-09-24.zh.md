# OpenETL-Go UI 产品与交互设计复审（2026-09-24）

## 结论先行

OpenETL-Go 的 UI 已经不是“只能填 YAML 的管理页”：它已经能让用户从总览发现异常、进入问题中心、定位到管道问题页，并进入 DLQ/重放路径；创建向导也已经接入连接、schema/introspection、preflight、YAML 和草稿。这个基础是正确的。

但从小团队自托管 ETL 产品的角度，它仍偏向“功能完整的工程控制台”，还没有始终把用户带向三个核心结果：

1. **把第一条安全的管道跑起来；**
2. **确认它正在推进，而非仅处于 running；**
3. **遇到故障时知道先修什么、能否安全重放、修完是否恢复。**

本轮将问题分为三类：

- **错误设计**：给出错误或不完整的操作事实，可能诱发错误判断；
- **不必要的用户成本**：功能可用但要求用户理解内部实现或猜测下一步；
- **可优化设计**：不会立即出错，但削弱首次成功、日常值守或可维护性。

> 证据范围：使用 Playwright 实际操作已构建前端的总览、管道、问题中心、详情、向导、DLQ、连接、设置，并检查 1280px/390px 布局。API 用浏览器层 fixture 驱动，故界面状态、导航、点击和响应式问题为实测；真实服务端请求成败另由容器 E2E 认证。

## 目标用户与核心 Job

### 主用户画像：兼任数据运维的应用工程师「小周」

- **环境**：5–50 条数据库 / Kafka / 文件同步任务；没有专职数据平台团队；生产问题往往由后端工程师轮值处理。
- **能力**：懂数据库、业务表和基础运维；不希望先理解 DAG、worker、插件 ABI、checkpoint 存储实现才完成一个同步任务。
- **触发场景**：上线业务同步、源/目标故障、CDC 延迟、DLQ 积压、计划任务未推进。
- **核心 JTBD**：
  > 当我需要把业务数据可靠地从 Source 同步到 Sink 时，我想以清楚的安全边界完成配置、验证和运行，并在异常时迅速知道应修哪里、能否重放、是否恢复，从而不靠猜测地保障数据交付。

### 产品北极星体验

不是“用户看过了多少页面”或“配置过多少 connector”，而是：

> **用户可以在不理解内部实现细节的前提下，安全创建、验证、观察并修复一条数据交付链路。**

相应的体验指标建议：

- 空环境到**首条 preflight 通过且首批写入已验证**的中位时间；
- 从 Issue 入口到**明确 remediation 或需要人工升级**的中位时间；
- DLQ 修复后**成功重放且剩余 backlog 可核对**的完成率；
- 用户把 `running` 错当为“健康且正在推进”的比例（应趋近 0）。

### 关键时刻

- **Aha moment**：用户完成 preflight，启动后看到首批成功写入、checkpoint 推进，并能从详情确认写入语义和风险边界。
- **Moment of truth 1**：在确认页判断“这条管道是否安全可启动”。这里不能出现变量残留、误导性状态或隐藏风险。
- **Moment of truth 2**：故障发生后用户是否能在 10 分钟内到达一个明确的 remediation，而不是只看到日志/指标。
- **主要流失触发点**：配置时必须理解太多内部对象；小屏上核心运维页面不可用；高影响按钮点后没有明确结果；重放后不知道是否恢复。

## 设计问题与建议

## A. 错误或危险的交互设计

### A1. 高风险批量操作确认内容不完整

**实测**：批量启动确认描述中 `{action}` 未替换；切换中文后仍有 `Cancel`、`Close` 英文。

**为什么是错误设计**：确认弹窗的职责是建立“用户意图 ↔ 实际影响”的最后一道一致性校验。操作名称缺失时，用户无法判断即将执行的是启动还是停止；本地化破损进一步损害生产工具的可信度。

**改进**：

- 标题、描述、确认、取消、关闭都必须本地化并有参数替换测试；
- 展示目标数、目标名摘要、被排除目标数，以及明确的 at-least-once/replay 影响；
- 确认后给出成功 / 失败 / 未执行计数以及对应链接，不只 toast。

**优先级**：P0，`UI-D.1` 已于 2026-09-26 交付（真实 app 容器 E2E D1.1–D1.2）。

### A2. 无可执行目标的批量按钮仍可点击且静默

**实测**：只选择 stopped 管道时，Stop 按钮可点，但没有 API 动作、确认框、toast 或解释。

**为什么是错误设计**：系统没有尊重“可供性（affordance）”原则：可点击意味着会执行或至少解释；静默返回会让用户质疑系统状态是否可靠。

**改进**：禁用不能执行的动作，并在可访问 tooltip 中说明原因；若保留点击，则出现明确 toast。工具栏应显示“1 可启动 / 0 可停止”，而不是只显示状态总数。

**优先级**：P1，`UI-D.2` 已于 2026-09-26 交付（真实 app 容器 E2E D2.1–D2.3）。

### A3. 把“重放”作为单点动作，而非恢复闭环的一环

**风险**：虽然已有确认和 dry-run，但从问题中心直接给出 `Repair & replay` 容易在用户还未完成连接测试、schema 修复或 preflight 前把注意力拉到“重放按钮”。对 at-least-once ETL，错误时机的 replay 会扩大重复或失败范围。

**改进**：按钮采用状态化文案：

- 未验证修复：`前往修复`；
- 修复可验证：`验证修复`；
- 验证通过：`Dry-run 重放`；
- 才进入：`重放 N 条记录`；
- 重放完成：`核对剩余 backlog / checkpoint`。

这不是禁止快速操作，而是让快路径依赖足够的安全证据。

**优先级**：P1，建议列为 UI-D 后的独立任务型闭环项，避免在 UI-D 中扩张范围。

## B. 不必要的用户成本

### B1. 首次创建的默认视图仍像“配置编辑器”而非“完成一项任务”

向导的功能很强，但用户面对的是模板、连接、schema、运行参数、转换、样例、YAML、预检的集合。工程师能理解，首次使用者难以知道什么是必须项、什么可稍后再调。

**优化原则**：每屏只推进一个承诺：

1. 我要同步什么业务数据？
2. 从哪个已验证来源读取？
3. 写到哪里，按什么写入语义？
4. 是否需要必要的数据处理？
5. 能否安全启动？
6. 启动后如何证明成功？

**具体改进**：

- 默认只露出必填字段与当前步骤相关风险；
- 运行参数、原始 JSON/YAML、少用 transform 放入“高级配置”；
- 已通过连接测试的 connection 标记为推荐，而非只列出类型；
- 让最终确认页包含“首批验证计划”，例如写入目标、预期行数/检查方式、如何看 checkpoint。

**优先级**：P1/P2，属于后续产品任务流项。

### B2. “问题中心”按技术信号列条目，而不是按用户要解决的事故组织

当前一条 sink outage 可能同时显示 last error、DLQ backlog、lag/checkpoint 等多个条目。技术上正确，用户会觉得“有四个问题”，但实际只需要修一个连接或目标服务。

**优化原则**：先按 incident/根因聚合，再显示影响维度。

**建议信息结构**：

```text
库存 Kafka 写入异常                           阻断
根因：sink write timeout
影响：24 条 DLQ · 最近 checkpoint 2 分钟前 · 79 条写入失败
下一步：测试 Kafka 连接 → 验证修复 → Dry-run 重放
```

用户可展开查看每个指标，而不是先理解每个指标才知道该修什么。

**优先级**：P2，需先确认后端是否能提供足够的错误关联 ID；不能仅靠 UI 猜测根因。

### B3. `Locate` 和 `Diagnose` 竞争同一目标

对于非专家用户，`Locate` 不解释结果，`Diagnose` 又可能跳转到不同 tab/DLQ。用户要先学会页面架构，才知道该点哪个。

**改进**：

- 主按钮以结果命名：`查看失败原因`、`修复并重放`、`测试连接`；
- `定位到管道` 放进更多操作或用为辅助链接；
- 若进入详情，应高亮具体 issue 或 node，并在返回时保持问题上下文。

**优先级**：P2。

## C. 响应式与值守场景的问题

### C1. 移动端不是“缩窄版桌面”，应当是“异常优先的值守端”

实测 390px 视口：Connections 整页宽度约 690px，Extensions/My Plugins 约 540px，Schedules 也有轻微溢出。用户需要横向拖动才能看到管理动作，破坏了手机值守的主要价值。

**设计建议**：

- 移动端总览 / Issues / DLQ：保留完整可修复路径；
- Connections / Schedules / Extensions：卡片化摘要 + `更多`；
- 表格仅在有明确、受限的内部横向滚动容器时存在，并显示视觉滚动提示；
- 删除、重放等危险操作在移动端保留文字标签，避免只留图标。

**优先级**：P1，`UI-D.3` 已于 2026-09-26 交付（D3.1–D3.9：390px containment/local focus + 1280px table）。

### C2. 小屏向导步骤条可滚动但没有发现性

实测 390px：只初始可见前 3 个步骤，第 4–6 步在横向滚动区域外。技术上并非不可达，但认知上容易被误解为没有后续步骤。

**建议**：移动端改为 `第 2 / 6 步 · Source` 或带自动滚动、渐变遮罩、进度条的横向导航。

**优先级**：P1，`UI-D.4` 已于 2026-09-26 交付（D4.1–D4.5：progress、affordance、local auto-scroll、keyboard/hash）。

## D. 信息层级与状态表达的优化

### D1. 自动刷新时间既像状态又像动作

顶栏以时钟值作为按钮文本，用户难以判断它是“上次刷新时间”“自动刷新倒计时”还是“立即刷新”。暂停后文本才变成状态。

**建议**：

- 主状态：`● 实时更新中` / `⏸ 自动刷新已暂停` / `⚠ 刷新失败，正在重试`；
- 次级信息：`上次成功刷新 23:36:54`；
- 单独的明确操作：`立即刷新`。

**优先级**：P2，`UI-D.5` 已于 2026-09-26 交付（D5.1–D5.9：三态、manual refresh、EN/ZH a11y）。

### D2. 总览需要更严格地隔离“行动、健康、累计”

当前总览已经优先展示待处理事项，这是正确方向；但同屏仍容易同时看到健康比例、累计写入、DLQ 和管道行。对于处理故障的用户，数值会造成注意力分散。

**建议布局**：

1. **现在要处理**：按事故/根因排序，最多 3–5 项；
2. **是否正在推进**：健康管道、stale checkpoint、CDC lag、最近成功写入；
3. **累计概览**：作为次级、可折叠或单独观察页；
4. **关键管道**：用户主动 pin 的少量业务链路，而非自动列出所有异常/所有管道。

**优先级**：P2，需要真实使用数据验证，不应只凭审美改版。

### D3. 用业务语义代替实现语义，但保留可展开的专家信息

`mysql_cdc`、`clickhouse`、`cdc_policy` 是有价值的专家信息；但它们不应是普通操作员第一眼最重要的信息。

**建议分层**：

- 首层：`订单同步 → 实时 → 写入正常 / 有 7 条待处理`；
- 次层：Source → Transform → Sink 路径、写入模式、延迟；
- 展开层：connector 类型、原始错误、node、checkpoint position、YAML。

这样不会隐藏技术能力，而是让不同熟练度的用户在恰当层级看到它。

## E. 信息架构建议（不建议直接大重构）

现有导航已有分组，方向正确。下一步不宜为了“更像 SaaS”而重做页面，而应根据频率和任务关系做减法：

| 用户意图 | 推荐入口 | 当前需要调整的重点 |
| --- | --- | --- |
| 今天是否有数据交付风险？ | 总览 / 问题中心 | 按事故和下一步行动组织，不按全部指标平铺。 |
| 管道是否在推进？ | 管道列表 / 详情 | 明确健康、推进、历史累计三种口径。 |
| 修复失败并重放 | 问题中心 → 详情 / DLQ | 串联修复证据和 replay，而不是把重放作为孤立按钮。 |
| 新增一条链路 | 总览空状态 / 新建管道 | 渐进披露，强调首批验证而不是完整配置。 |
| 管理连接 | Connections | 展示健康、引用关系、最后成功测试；移动端卡片化。 |
| 查能力 / 扩展 | 连接器目录 / 扩展 | 保持为低频辅助入口，避免与日常运维同权竞争。 |

不建议：

- 把 DAG、worker、plugin 编译重新升格为一级日常操作；
- 用更多卡片、颜色、仪表盘“美化”来替代明确的下一步；
- 为了移动端塞入更多底栏入口，导致日常导航变拥挤。

## 建议的后续实验与验证

在实施较大产品设计调整前，应以真实用户任务验证，而不是只根据专家评审：

1. **首次任务可用性走查**：找 3–5 名熟悉业务库、但不熟悉 OpenETL 的工程师；给出“把 orders 同步到 ClickHouse，并验证首批数据”的任务；记录卡点、完成时间、是否编辑 YAML。
2. **故障修复走查**：注入 sink timeout + 20 条 DLQ；要求用户“恢复交付且说明是否存在重复风险”；记录是否误点 replay、是否能判断修复成功。
3. **移动端值守走查**：390px 下要求用户测试连接、查看失败、dry-run/replay；通过标准是不用横向拖动整页、不需要记忆隐藏入口。
4. **文案理解测试**：比较 `Diagnose/Locate` 和以结果命名的动作文案，观察首击正确率。
5. **指标口径测试**：展示 `running`、`healthy`、`last successful write`、`checkpoint age` 的组合，问用户“此管道是否在推进、你依据什么判断”。

## 优先级建议

### 已交付：UI-D（低风险、高信任收益，2026-09-26）

1. 批量确认参数替换和 EN/ZH 完整本地化；
2. 无可执行目标的批量按钮状态/反馈；
3. Connections、Schedules、Extensions/My Plugins 的 390px 溢出；
4. 小屏向导步骤的进度和发现性；
5. 自动刷新控件语义与可访问名称。

证据：重建真实 app 容器的 `hack/e2e-ui.sh` **209 passed / 0 failed**；逐项 D1–D5 矩阵见 [UI-D tasks](./iterations/UI-D-interaction-mobile-hardening/tasks.md)。

### 下一批（需产品验证，但价值高）

1. 故障案例聚合与“修复 → 验证 → 重放 → 核对”闭环；
2. 首次任务向导的必填/高级信息分层，以及首批验证计划；
3. 总览的“行动 / 推进 / 累计”信息架构拆分；
4. 面向连接的健康、引用关系和删除影响解释。

### 不建议此刻做

- 大规模视觉重做或迁移组件库；
- 新增复杂图表或模拟 SaaS 分析面板；
- 新建独立 UI 数据模型绕过现有 descriptor、preflight、pipeline spec；
- 在没有真实 incident 关联证据前，纯前端猜测根因并强行合并所有 Issues。
